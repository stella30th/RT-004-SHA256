========================================================
ORACLE-AWARE PROMPT REFINEMENT PROCEDURE
========================================================

For EACH task, perform the following reasoning internally BEFORE generating the JUnit test.

Do NOT print your reasoning.
Output only the final Java test class.


1. SOURCE-FIRST SEMANTIC TRACE
------------------------------
Read TARGET_SOURCE carefully, line by line.

Treat TARGET_SOURCE as the authoritative behavioral specification.

Do NOT replace the implementation's behavior with:

- conventional behavior;
- textbook definitions;
- library-standard behavior;
- domain assumptions;
- typical API semantics;
- what the method name appears to imply.

If the implementation behaves differently from conventional expectations, test the implementation's actual behavior.


2. EXACT API EXTRACTION
-----------------------
Before creating tests, identify exactly:

- constructor signatures;
- public method signatures;
- argument types;
- return types;
- accessible state;
- accepted input formats;
- special symbols/constants;
- null behavior;
- boolean sentinel behavior;
- empty-value behavior;
- possible exceptions.

Never call an API that is not present in TARGET_SOURCE.


3. PRECONDITION ANALYSIS
------------------------
Determine whether each method requires setup before invocation.

Check whether behavior depends on:

- constructor initialization;
- earlier method calls;
- internal lists/maps;
- inserted values;
- accumulated counters;
- player symbols;
- validation vocabularies;
- object state;
- stored records;
- collection membership.

Do not assume that a method is stateless.


4. STATE-TRANSITION TRACE
-------------------------
For stateful classes, explicitly trace internally:

Initial State
    ↓
Operation 1
    ↓
State after Operation 1
    ↓
Operation 2
    ↓
State after Operation 2
    ↓
Expected observable result

Pay special attention to:

- cumulative values;
- additive updates;
- decrement operations;
- counters retained across calls;
- toggles;
- removals;
- mutations;
- order creation;
- stored objects;
- repeated method calls.

Do not assume that an "update" operation performs assignment.
Trace exactly what TARGET_SOURCE does.


5. ORACLE DERIVATION
--------------------
For every assertion, independently derive the expected result from TARGET_SOURCE.

For numeric results:
- trace the arithmetic exactly;
- recompute the expected value;
- account for previous state changes.

For strings:
- preserve exact casing;
- preserve character order;
- follow substring/index logic;
- follow transformation loops exactly.

For collections:
- determine exact contents;
- determine ordering if relevant;
- account for filtering and prior state.

For booleans/null:
- identify the exact branch reached;
- use the exact value returned by that branch.

For exceptions:
- inspect whether the source validates the input before indexing/accessing;
- if no guard exists and the operation naturally throws, test the exception rather than assuming false/null.


6. ORACLE CROSS-CHECK
---------------------
Before finalizing EACH assertion, verify all of the following:

A. Does the invoked API actually exist?

B. Does the test setup satisfy the source's preconditions?

C. Which exact control-flow branch will execute?

D. Does the expected value follow from that branch?

E. Did an earlier call change internal state?

F. Am I assuming conventional semantics that are NOT implemented?

G. Am I assuming capitalization, ordering, parsing, or encoding behavior that differs from the source?

H. Am I expecting false/null when the implementation actually throws?

If any answer reveals a conflict, correct the test oracle before output.


7. BOUNDARY AND EXCEPTION ANALYSIS
----------------------------------
For invalid/boundary input, explicitly distinguish among:

- returns false;
- returns null;
- returns empty value;
- ignores input;
- clamps input;
- performs operation anyway;
- throws runtime exception.

Never automatically assume invalid input returns false.


8. DOMAIN-VALUE ANALYSIS
------------------------
When TARGET_SOURCE accepts special values or symbols, derive them exactly from the source.

Examples include:

- accepted validation strings;
- player characters;
- status values;
- delimiters;
- character casing;
- board markers;
- sentinel values.

Do not substitute common alternatives.


9. FINAL CONSISTENCY PASS
-------------------------
After drafting the complete test class:

- reread TARGET_SOURCE;
- re-evaluate every assertion;
- retrace every state-changing call;
- verify every expected result once more;
- check boundary behavior;
- check casing/order;
- check null/boolean behavior;
- check exceptions;
- check constructor and method signatures.

Correct any inconsistent oracle before generating the final output.
